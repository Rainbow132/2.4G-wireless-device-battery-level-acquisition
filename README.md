# 无线外设私有协议电量逆向获取通用指南

当面对市面上琳琅满目的无线键盘和鼠标时，由于厂商大多采用私有协议（如中颖、北欧半导体公版 SDK 等修改版）[1.1.4, 1.4.5]，系统默认无法直接读取它们在 2.4G 模式下的电量。通过本篇指南，你可以系统地了解如何利用官方驱动程序，一步步逆向分析并用代码获取任意无线外设的电量。

---

## 核心技术背景：两大主流无线方案特征

在国产品牌中，绝大多数无线外设的 2.4G 接收器方案都可归为以下两类：

### 1. 中颖 (Sino Wealth) / Compx 方案（多见于键盘，如迈从、狼蛛）
* **物理特征**：使用 **20 字节** 或 64 字节的小数据包 [1.2.2]。
* **Report ID**：通常为 `0x13`（十进制 19）或 `0x06` [1.2.2]。
* **多包机制**：在发送初始化/查询指令后，接收器会连续吐出多个不同的回包（例如：第一个包是指令 ACK 确认包，第二个包才是真正的状态电量包）。
* **校验机制**：包尾通常带有标准的**累加和校验和（Checksum）**，用于校验数据传输完整性。

### 2. 北欧半导体 (Nordic Semiconductor) nRF 方案（多见于鼠标，如达摩鲨、VGN、ATK）
* **物理特征**：使用 **64 字节** 的无 Report ID（DMS 中显示为 `Report ID: -1`）数据包。
* **双通道/槽位路由**：为了兼容多设备或高刷模式，接收器具有“槽位路由（Device Slot）”机制。
  * **槽位一 / 1K 模式**：通信报头以 **`0x01`**（1）开头。
  * **槽位二 / 高刷（4K/8K）模式**：通信报头以 **`0x41`**（十进制 65）开头。
* **系统写入保护**：由于没有 Report ID，在 Windows 下利用 Python 写入 64 字节指令时，必须**强制在首字节填充 `0x00` 虚拟 ID**。

## 第一阶段：设备控制通道探测与隔离 (Find the Gateway)

Windows、macOS 等操作系统为了防范键盘记录器等恶意软件，会严格封锁标准的键盘鼠标输入接口（Usage Page `0x01`）。我们必须找到厂商留下的“免驱自定义控制通道（后门）”。

1. **查询设备信息**：在设备管理器或 HID Explorer 在线工具中，过滤目标外设接收器的 VID 和 PID [2.1.2]。
2. **寻找自定义通道（Usage Page）**：
   * 观察设备暴露的所有接口描述。
   * **不要选择**：`Usage Page: 0x01` (这是系统保护的普通输入接口)。
   * **锁定目标**：寻找带有 **`0xFF00` ~ `0xFF0A`** 这样厂商自定义页（Vendor-defined page）的接口（例如键盘常用 `0xFF02`，鼠标常用 `0xFF0A`） [2.1.2, 2.4.1]。只有打开这个接口，你才拥有对设备的自定义数据读写权限。

## 第二阶段：数据流监控与抓包 (Sniffing)

一旦锁定了控制通道，我们就需要通过运行官方驱动，截获它和设备之间的对话字节流 [1.1.8]。

### 途径 A：网页端驱动（WebHID 拦截法）
如果设备有网页端驱动，这是最简单的方式：
1. 打开网页驱动，不要连接设备，按 `F12` 切换至 **Console** 控制台。
2. 注入一段 `Monkeypatch` 代码，代理浏览器的 `HIDDevice.prototype.sendReport` 方法和 `inputreport` 事件监听函数。
3. 点击连接设备，控制台就会以非常规整的十六进制数组格式，直接打印出每次色彩同步、电量查询的发送（DOWN）和接收（UP）包。

### 途径 B：本地客户端驱动（DMS 软件抓包法）
如果只有本地 `.exe` 安装程序，可以使用 **Device Monitoring Studio (DMS)** 抓包：
1. 打开 DMS，在左侧列表中通过 `Next connected device`（插拔接收器激活）或者刷新设备树，找到目标接收器设备 [1.1.8]。
2. 右键点击它选择 `Start Monitoring`，勾选 **`HID View`** 和 **`URB View`**。
3. 中间窗口开启监控后，**启动官方本地驱动客户端** [1.1.8]。
4. 让客户端读取或刷新出外设电量（记录此时驱动上显示的精确百分比，例如 `92%`）。
5. 此时 DMS 会疯狂刷新出 **UP（接收，设备发给电脑）** 和 **DOWN（发送，电脑发给设备）** 报文。

## 第三阶段：报文解构与逻辑推演 (Reverse Engineering)

抓包完成后，通过控制变量和逻辑推算，找出电量的字节位置和查询口令。

### 1. 电量数据字节定位
* 将抓包时驱动显示的电量（如 `92%`）转换为十六进制（`92` $\rightarrow$ `0x5C`；`51` $\rightarrow$ `0x33`） [1.1.2]。
* 翻阅接收报文（UP 包），寻找在哪一个字节位置出现了这个数值。
  * 例如，在鼠标回包中：`65, 0, 140, 1, 0, 0, 92 ...` 发现 `92` 刚好出现在第 7 个字节（索引 6） [2.1.2]。
  * 如果电量发生消耗（从 `58%` 变到 `57%`），观察回包中对应字节是否也发生了同步递减（从 `0x3A` 变到 `0x39`），以此确认变量。

### 2. 逆向推算查询口令
在设备刚刚吐出电量包（UP）之前，电脑向其发送（DOWN）的那一个包，就是**查询/唤醒指令** [1.1.8]。
* **键盘 (Compx 方案)**：
  * 发送包：`13 05 01 00 ...` 
  * 接收包：首先返回 `13 05 01...`（握手回执，无电量），随后连续发送第二个包 `13 0A 01...`（状态包，含电量）。
* **鼠标 (Nordic 方案)**：
  * 槽位1/1K模式发送包：`1, 0, -127 (129), 1 ...` 
  * 槽位2/高刷模式发送包：`65, 0, -127 (129), 1 ...`（注：由于是 Raw 64 字节无 ID 设备，在 Windows 写入时首字节需补 `0x00` 虚拟 ID，即发给 `hidapi` 的数组开头是 `0x00`）。
  * 接收包：返回 `65, 0, 140, 1, 0, 0, [电量]...`。

## 第四阶段：代码实现与双保险机制 (Implementation)

在用 Python 实现时，我们经常会遇到：*“只有在驱动打开时能读到，一旦关闭驱动，脚本就只能读到离线/休眠（Offline）数据包”*。

### 为什么会发生这种情况？
由于无线节能机制，当官方驱动关闭时，接收器不再活跃，鼠标/键盘无线芯片会在几秒内进入深度休眠。此时运行 Python 脚本查询，接收器只会立刻扔给你一个离线缓存包。如果你的 Python 脚本只读取了一次就断开连接，就永远无法触发接收器的隔空无线电唤醒。

### 核心解法：自适应循环查询（Keep Alive Polling）
Python 脚本必须模拟官方驱动的行为：
1. 开启一个最长 3 秒的持续循环。
2. 循环中，**每隔 250~300 毫秒向接收器写入一次查询指令**，高频敲门以强行唤醒无线接收器。
3. 持续高频读取接收缓冲区。
4. **不要在收到离线包时立刻退出**，只做离线标记，允许循环继续往下读取。
5. 只要键盘/鼠标在无线电波的呼唤下被物理唤醒（可以晃动一下鼠标），后面几毫秒的包就会瞬间变成带有电量的在线数据包。此时读取到电量后立即 `break` 退出。
